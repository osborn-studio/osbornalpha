The following are **new mechanism-specific blockers**, rather than additional listings of the unresolved N11/N14/N20 concerns.

| Severity | Section | Issue | Fix |
|---|---|---|---|
| **P1 · R4-1** | §§4.3, 4.5 | **Abandonment cannot execute as specified.** The fact trigger permits deletion only when the owning run is already `abandoned`; both `begin_sync_run` and `abandon_sync_run` explicitly delete facts **before** marking the run abandoned. Any abandoned run containing facts therefore makes recovery fail. The special deletion flag applies only to filings. | Within one transaction, validate that the run is staged, mark it abandoned, then delete its facts and eligible empty filings. Reject abandonment of published runs. |
| **P1 · R4-2** | §§4.5, 5.3–5.4, 6.1 steps 7–8 | **Conflict handling modifies public data before publication.** An existing published value is quarantined in a separate RPC before `publishRun`. If the incoming run then fails or is abandoned, its candidate disappears while the previously published value remains hidden. This violates the promised all-or-nothing run visibility and can permanently remove the authoritative value without a replacement publication. | Record pending conflict dispositions and apply changes to existing published facts atomically with run publication; abandoning an unpublished run must leave published facts unchanged. |
| **P1 · R4-3** | §§5.3, 7.3 | **Conflict state disappears from subsequent conflict detection.** Publish A=10; ingest B=20 and quarantine both; then ingest a distinct filing C=10 on the same K/date. The prescribed comparison considers only `ok` or this run’s staged rows, so neither A nor B blocks C; C becomes public despite the unresolved conflict. | Maintain persistent conflict-group eligibility for active K/date interpretations, including quarantined members; later arrivals must join the unresolved group. Validate the whole group when resolving it. |
| **P1 · R4-4** | §§4.5, 7.1–7.3 | **Promotion checks open references, not publication eligibility or a binding conflict decision.** First, a quarantined fact from a still-staged run can be promoted and become public when its filing’s mapping is already active. Second, after a conflict is resolved, an independent identity-item acceptance can promote an unchosen conflicting value because the conflict item is no longer `open`. `chosen_fact_ids` is not recorded as an enduring eligibility constraint. | Require a published owning run and eligible active interpretation; persist the chosen conflict value/IDs and enforce that decision on every promotion. Serialize resolution, association checks, and promotion with ingestion using a shared lock protocol. |
| **P1 · R4-5** | §§4.6, 4.8, 6.1, 8 | **The 10,000-row contract is silently cut to 1,000 in the landed local API configuration.** `read_facts` returns a table, while [supabase/config.toml:9](/Volumes/AIMATE_WORK/Developer/CodeX/OsbornAlpha/.claude/worktrees/data-foundation-2/supabase/config.toml:9) sets `max_rows=1000`. A 1,001-row history can arrive as 1,000 rows with no SQL overflow flag; the special flag on row 10,000 can itself be discarded. Planning can miss conflicts and derivation can replace complete metrics with incomplete results. Even genuine `truncated=true` has no prescribed internal rejection. | Return a single envelope containing rows and completeness metadata, or otherwise establish transport-safe snapshot delivery. Planning and materialization must refuse incomplete input; public truncation must be reported reliably. |
| **P1 · R4-6** | §§4.4–4.5, 7.3, 8 | **`based_on_run` does not identify the fact state used for computation.** Calculation A reads run R; a promotion changes facts and calculation B writes updated metrics, still based on R; A then overwrites B because no newer run exists. Separately, publication uses the scope-row lock while replacement uses an advisory lock, so a newer publication can commit between the freshness check and metric replacement. | Introduce a fact-state revision incremented for publication and eligibility changes. Return it with the fact snapshot; validate it during replacement under the same lock used by those mutations. Run identity can remain provenance, but cannot be the sole freshness token. |
| **P1 · R4-7** | §§4.5, 4.7–4.8, 6.4 | **Scope reconciliation has no permitted write path.** `upsertScope` must create/update scope rows before lease acquisition, but direct writes are revoked, the production adapter is RPC plus read-only queries, and the function set contains no scope-reconciliation function. Applying the universal lease precondition would also prevent creation of the first scope row. | Add an explicitly lease-independent scope-reconciliation RPC, restricted to service role, that changes only the permitted scheduling inputs and preserves existing lease/schedule state. State the exceptions to the universal write-function precondition. |

PostgREST documents that its row cap applies to table-returning functions as well as tables/views; production’s configured cap was not inspected. [PostgREST configuration](https://docs.postgrest.org/en/stable/references/configuration.html#db-max-rows)

The cninfo column-level grant in §4.8 is an explicit exception to §4.7, not an unrestricted fact-publication bypass: it excludes `mapping_gen` and fact status. I would reconcile the contradictory wording and define stale-link-update handling, but **would not classify that exception alone as P1**.

External semantics remain unverified: Tushare revision retention, announcement dates and pagination, and cninfo correction-title/document identity require the recorded provider checks in §§6.3/15; the findings above do not assume those providers behave incorrectly.

**Final verdict: not ready for an implementation plan—the blocking items are R4-1–R4-7 and the still-unresolved revision-compatibility requirement N14; owner decisions A/B/C remain pending.**
