| S1 | P1 | §3.1 `issuers_topology_guard`; §3.2 | **The new topology guard fails open.** On a connection where the setting is absent, `current_setting(..., true)` returns NULL; `NULL <> 'on'` does not enter the rejection branch. Direct topology updates can therefore bypass scope locks and revision invalidation. The transaction-local flag also remains enabled after a successful function call until transaction end. Landed `issuers.ts` does **not** update topology: its `status:'active'` occurrences in enrichment updates are predicates. | “Reject topology changes when `current_setting('entities.allow_topology_write', true) IS DISTINCT FROM 'on'`. Both topology functions must save the previous setting and restore it before returning, including handled exception paths. Test direct updates on a fresh connection and after a topology function returns within the same transaction.” |
| S2 | P2 | §§3.2, 5.3–5.4 `read_filing_facts` | **The unrestricted reader makes natural-key binding ambiguous across generations.** Plan 2 permits the same filing/key in multiple mapping generations, potentially with different values. The new reader returns all of them, but reconciliation still resolves a natural key to one `fact_id` without a selection rule. It can compare an obsolete row while leaving the active row unchecked. | “Ordinary reconciliation binds to the filing’s active mapping generation and published runs, accepting `ok` or `quarantined` status. Explicit quarantine rechecks bind to `payload.fact_ids` regardless of generation and never substitute another row. Multiple eligible rows produce an explicit ambiguity outcome. Candidate-adoption duplicate checks use Plan 2’s complete candidate key, including `mapping_gen`; older generations alone do not constitute duplicates.” |
| S3 | P1 | §§5.5–5.6; §3.2 reconciliation functions | **Lease-loss handling discards counters but not business effects.** A worker can lose its claim, then quarantine facts or overwrite `latest_result` before its final `done` update detects lost ownership. Marking its reconciliation rows `superseded` does not reverse those effects; stale evidence can influence restoration. | “Fence every reconciliation-derived mutation with the cursor’s cycle, member, batch and attempt token. Validate ownership and unexpired lease under a cursor row lock in the same transaction that applies quarantine, updates `latest_result`, or creates actionable work. A failed fence applies no business mutation. Only accepted attempts may contribute results or settlement counters.” |
| S4 | P2 | §5.5 claim/retry predicate | **Failed members cannot take the promised retry path.** The concrete claim predicate permits only `pending` and `claimed`, while exceptions set `failed`. A first failure therefore remains below three attempts forever, preventing settlement. | “A cursor is claimable when `state='pending'`, or `state='claimed' AND claim_until < clock_timestamp()`, or `state='failed' AND attempts < 3`. Claim atomically, replace ownership, increment attempts and clear the previous error. Failed rows with three attempts are terminal.” |
| S5 | P2 | §3.1 `drc_done_accounted`; §5.5 settlement | **The new accounting constraint accepts unaccounted completion.** All three counters are nullable; PostgreSQL accepts a CHECK whose result is NULL. A `done` row with a missing counter can therefore pass the advertised invariant, and aggregation can omit that member’s missing counts. | “Require `expected >= 0`; counters must be nonnegative when present. For `state='done'`, require all three counters `IS NOT NULL` and their sum equals `expected`. Before settlement, assert every done member satisfies this invariant; never coalesce invalid done counters to zero.” |
| S6 | P2 | §§4.6, 5.4, 5.6; Plan 2 §7.3 | **The new `reconcile_review` exception contradicts the exhaustive dispatcher.** §5.6 requires status-only handling through the generic path, but §4.6 sends every unlisted `facts.*` reason to `resolve_facts_quarantine`, which performs fact eligibility/promotion and materialization. | “Dispatch `reconcile_review` explicitly to the generic guarded status transition for both acceptance and rejection; perform no fact promotion or materialization. Add it to the exhaustive dispatch table and its tests. Retain the three specialized reconciliation/adoption branches and use the Plan 2 resolver only for remaining reasons.” |
| S7 | P2 | §§3.1, 6.2 `dq_calendar_passes` | **A unique unfinished pass does not ensure complete or serialized traversal.** The new pass stores only a count and cursor, not frozen membership or worker ownership. Concurrent workers can overwrite progress; an issuer added below `cursor_after` is skipped while the pass can still advertise successful coverage. | “Freeze the ordered issuer membership when creating a pass. Permit one leased worker per market/pass; fence expectation replacement and cursor advancement with its ownership token. Advance only after successful replacement, and finish only when every frozen member has completed. Scope additions enter the next pass; failures remain retryable and prevent successful completion.” |
