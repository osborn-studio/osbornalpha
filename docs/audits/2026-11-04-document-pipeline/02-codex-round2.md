The second draft still has implementation-blocking contract failures. Evidence insertion cannot execute in the stated PostgREST transaction sequence, evidence links prevent abandoned-run cleanup, and regeneration cannot reliably replace previously published facts. The new latest-document view also leaves a private-data exposure path unless its security semantics are specified explicitly. Several round-1 fixes are therefore partial despite the revised prose claiming closure. This was a read-only review against the listed repository files and Plan 2 draft 8; no files were changed or tests run. Verdict: not ready.

**Checks that do not establish additional defects**

- **`fact_citations` RLS recursion:** I found no recursive dependency in the stated design. Its policies reference `financial_facts` and citation/document rows; Plan 2’s fact policy is `using (status='ok')`, and the document policy is `permission='public'`. Neither points back to `fact_citations`. The referenced relations have SELECT grants. Primary-key lookups make the design plausible, but actual query performance remains unmeasured. N4 concerns the separate latest-document view.
- **`candidates_status` default:** `default 'n/a'` itself is consistent with `finish_document_extract` explicitly selecting `pending` for eligible Chinese HK reports. The defects are retry selection, English comparison and overly broad regeneration.
- **Cache headers:** The private-response exception now overrides the public cache helper. The actual helper in `src/lib/entities/resolve.ts` returns ``public, s-maxage=${secs}, stale-while-revalidate=600``; §9 now limits its use appropriately. Historical filtering is still wrong independently of caching, as N18 describes.
- **Repository corrections:** The migration-order rule matches `scripts/ci/research-checks.ts`. The audit contract matches `src/lib/research/store.ts` and `20260705000000_research_os_tables.sql`: `object_type` is required and the JSON column is `detail`. The existing CN/HK collectors do write `available_at: clock().toISOString()`, so §2’s revised description is accurate.

**Items I cannot verify from the repository**

- **Source completeness:** I am unsure of EDGAR historical/index response guarantees, HKEX result/range limits and bilingual pairing, and cninfo category values. The landed collectors and fixtures do not establish ten-year completeness. These remain explicit prerequisites, not verified implementation assumptions.
- **Runtime feasibility:** `package.json` confirms Next `15.5.28`, Node `>=22.19.0 <23`, and no PDF dependency. It does not establish that the eventual `pdfjs-dist` version loads or fits production budgets. The proposed one-document smoke test does not establish performance for the largest in-scope reports.
- **Storage and PostgREST:** `scripts/s4/local-db.ts` creates a `storage.buckets` table stub, not a Storage service or PostgREST deployment. Duplicate-upload behavior, signed URLs, deployed row limits and RLS query plans require service-level validation.
- **Deployment configuration:** I am unsure of the actual Vercel plan, function memory configuration and production secrets. Their presence cannot be inferred from `vercel.json` or local source.
- **Golden-set evidence:** Two issuers, exact reporting periods, independent transcription and actual evaluation results remain future work. The current spec defines an evaluation procedure; it does not supply evidence that the extractor meets it.
- **Remaining placeholders and unsupported estimates:** §16 still leaves `roe_annual` undecided. The 19.5-person-day estimate has no work breakdown supporting its precision; table-clustering thresholds have no measured validation; the seven-day polling window has no source guarantee; and the 300-second signed-URL lifetime is justified by unrelated function duration. Conversely, the 50 MiB object limit and 2% CF tolerance do have stated repository precedents, so they should not be described as invented numbers.
