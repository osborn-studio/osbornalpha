| **R2-1** | **P1** | **3597–3604, 3615–3619, 9340–9356** | **GC reclaim introduces a stale-collector deletion race.** Collector A claims hash H and pauses before storage removal. After one hour, B reclaims H, deletes the object and index. A writer then registers, uploads and stages H successfully. A resumes and unconditionally removes the same `sha256/H` object. The final SQL check cannot restore it. Claims return only hashes, with no ownership token. **Fix:** make old deletion requests incapable of targeting a new object incarnation—for example, generation-specific storage keys with token-checked index finalization—or retain exclusive ownership through deletion with recovery that cannot overlap an old remover. A token check immediately before deletion alone still leaves a race. Test this exact reclaim → re-upload → stale-delete sequence. |
| **R2-2** | **P1** | **7539–7551; 9875–9885** | **Delist conflicts remain eligible for published aggregates.** If a stored closed window ends after a subsequently discovered delisting date, reconciliation only writes `dq_quarantine` and continues. The membership stays `ok`; aggregation reads membership candidates without consulting that quarantine. Period ends between delisting and the incorrect stored end therefore still include the issuer. **Fix:** transactionally supersede the incorrect membership with a corrected K3-bounded version, preserving lineage. If correction requires review, explicitly block affected publication until resolved. Add a two-run test with a previously closed window and a newly learned earlier delisting; assert exclusion at an intervening period end. |
| **R2-3** | **P2** | **8085–8093, 8185–8195, 8208–8209; 3067–3081** | **SIC completion is fenced, but its data writes are not.** A worker can pause beyond its lease, lose ownership to B, then resume and apply its old SIC response before B applies the newer response.
