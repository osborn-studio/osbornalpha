Paired production **read-only component profiles**, over the same constructed JSON payload selected by one known public manifest hash, measured:

| Component | Execution ms | Temp blocks read | Temp blocks written |
| --- | ---: | ---: | ---: |
| Typed `json_to_record`, including payload construction | 2,115.642 | 891 | 1,718 |
| Direct JSONB extraction, including payload construction | 861.557 | 0 | 827 |
| Direct JSONB extraction, reversed-order repeat | 488.142 | 0 | 827 |
| Typed `json_to_record`, reversed-order repeat | 615.076 | 891 | 1,718 |

The initial plans reported 186 shared buffer hits. The record function executed once; its own temporary reads/writes were 891 each. The shared payload CTE accounts for 827 temporary writes in each profile. On the reversed-order repeat, the timing gap narrowed substantially: direct 488.142 ms versus record 615.076 ms. CPU/cache contention is not isolated. These observations support avoiding the record spill; they do not establish a guaranteed 2.5x speedup, end-to-end latency guarantee, or resolution of the production timeout.

The parent correlated the earlier ID-selected roundtrip and hash-selected record profile to **the same single row**. The initial `length(body::text)` value, 6,774,474, counts characters; `octet_length(body::text)`, 6,775,060, counts bytes. The 586 difference comes from multibyte text, not different payloads. The earlier different-row interpretation was incorrect.

The forward migration adds `macro_put_manifest_json(jsonb)` with one **unnamed** argument, the [documented PostgREST mechanism](https://docs.postgrest.org/en/v14/references/api/functions.html#functions-with-a-single-unnamed-json-parameter) for accepting the raw JSON request body. PL/pgSQL prevents SQL-function inlining. The security-invoker wrapper requires exactly the original seven parameter keys, rejecting both missing and unexpected envelope keys before delegation. Scalar coercion remains unchanged. It delegates all seven arguments to the unchanged original RPC, preserving table constraints, full JSONB body equality on hash conflict, concurrent identity and complete provenance. PUBLIC, anon and authenticated execution are revoked; service_role alone receives execution. Supabase transport selects the new endpoint with the same complete JSON body. Other transports and the original RPC remain available. No cache, retry, timeout, compute, route diagnostic or evidence-reduction change is included.

A metadata-only pre-read was rejected: the SQL API accepts caller-supplied hashes, so matching the stored hash alone cannot replace the existing complete-body conflict check. A fully validated pre-read would also reintroduce the large response transfer removed by the earlier metadata optimization. This change instead addresses the measured gateway conversion boundary.

The loopback login used the reported 8-second caps, 2,184 kB work_mem and disabled JIT; hardware, PostgreSQL minor version and workload differ from production. These checks establish dispatch and correctness, not production performance. Committed PostgreSQL coverage additionally checks concurrency, malformed requests, service-only execution, unnamed argument metadata, unchanged constraints and migration replay. The adapter routing regression failed before implementation.

This corrects a compatibility blocker missed by the initial MiniMax review.
