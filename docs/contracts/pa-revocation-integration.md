# Revocation integration constraints from existing PA code

Implementation checkpoint, 2026-10-04. This is an execution note, not a deployed interface.

PA currently stores one mutable row per `(user_id, grant_id)` in `pa_bridge_grant`. `ProcessingGrant` has no version counter. The current `pa_bridge_event` replacement is in migration `20260922120000_pa_reader_bridge.sql` (not only the original bridge migration). Rights changes update all grant policies for the source, then upsert the selected grant. Scope sequence also includes ordinary reading events. Therefore neither the current grant row nor filtered outbox positions can directly satisfy the new versioned contiguous revocation feed.

Next producer implementation must:

1. Add explicit grant-version snapshots and a separate per-scope revocation head/event sequence. Reuse the existing owner advisory lock order; allocate committed positions transactionally, not via a sequence that leaves rollback holes.
2. Preserve all affected prior grant versions on rights changes. Revoke all relevant source versions on source withdrawal and all relevant scope versions on scope revoke. An idempotent replay must not add another position.
3. Define an explicit cutover epoch. A newly recorded current snapshot is evidence only from cutover onward, not reconstructed historical consent. Legacy Alpha bindings with unknown version remain ineligible for production processing until explicitly rebound/reimported against a recorded snapshot.
4. Return head and bounded page from one consistent database snapshot with server publication time. Signing uses only that snapshot; a transport service must not forge a new heartbeat over stale cached state. Feed reading uses a narrow scoped identity, not a generic service-role endpoint.
5. Add export metadata associating source/grant/version with the exact signed candidate; preserve the existing additive schema/extension rules. Verify producer and consumer agree before release.

Next consumer implementation must add a trusted feed registration, narrow revocation-only role, owner-serialized inbox/cursor transaction, duplicate-ID consistency and rollback tests. Its transaction must revoke matching bindings before committing its new cursor. Ordinary S4 runtime credentials must not acquire revocation grants. `assertRevocationFresh` must use committed trusted checkpoints selected for the binding's exact scope, and grant-expiry checks remain separate.

Acceptance must exercise rollback between inbox and binding mutation, duplicate delivery after commit, missing pages, concurrent workers, scope separation, unknown legacy versions, and stale heartbeat rejection on actual write and display paths. The current pure verifier and freshness guard do not provide these database or runtime guarantees.

## Approved manifest reference adapter (candidate only)

`prepareRevocationCandidate` validates an existing operator-approved candidate through `prepareCandidate` before interpreting `manifest.extensions['pa.revocation_reference']`. The extension must match PA's `pa-grant-reference/v1` shape, the trusted registered feed and scope, and the verified source and grant. It validates canonical observation time (no later than the candidate manifest), a positive int32 grant version and an int64 decimal export watermark. Missing references are rejected; legacy versions are never guessed.

Manifest extensions are not covered by `payload_digest`. The existing `approvedManifestHash` check is therefore mandatory, alongside `approvedPayloadHash`. Changing only the reference while keeping payload bytes intact is rejected unless the trusted operator approval itself changes. This adapter does not create approvals and does not provide a new signature-verification endpoint; callers must not accept binding or feed registration from an upload.

The result is only validated metadata. It does not insert a binding map, advance a feed cursor, check a persisted tombstone or establish current freshness. Next, implement candidate registration in a READ COMMITTED owner-serialized transaction against the existing approved binding and exact registered feed; require a caught-up fresh checkpoint at least through the exported watermark and reject revoked versions. Production S4 remains hard-disabled.

Opus5.5 review identified an authority gap for an in-range but wrong grant version and loss of existing error codes. The adapter now also requires a trusted `ExpectedGrantReference` (source, grant and version as well as feed/scope) and compares all identity fields, including the existing trusted config's grant ID. This dependency must be derived from authenticated PA export metadata/operator registration, never copied from the uploaded extension. Obtaining and persisting that authority remains unimplemented; this helper is not wired to an endpoint. No invented grant_version field was added to the frozen ProcessingGrant schema.

Existing `prepareCandidate` errors now propagate unchanged. Tests distinguish manifest approval failures (`policy_blocked`), identity/metadata failures, actor/revoked binding rejection and input-size limits. The manifest-only substitution test changes a valid earlier observation time so rejection specifically proves the manifest hash gate. Missing-reference input first proves the base candidate validator succeeds. Final task_9c65db64 passes revocation and ingest tests, typecheck and lint; full default regression passed before these final audit fixes (task_7c507cf3). Final fixes host-verified, not independently re-audited. Observation time is descriptive cutover metadata, not a grant-validity proof; no arbitrary lower bound tied to article observation was introduced.

## Existing-binding registration transaction (candidate only)

`registerCandidateReference` loads an existing operator-approved binding from the database while holding the canonical owner advisory lock and binding/feed row locks under READ COMMITTED. It runs the approved candidate/reference checks against that stored binding, matches the exact registered feed scope, checks database-clock grant expiry and committed caught-up freshness, and requires the cursor to have reached the export watermark. Conflicting mappings for the same binding fail closed. Mapping insertion remains subject to the existing tombstone trigger, including duplicate delivery; no cursor or approval is created or updated.

The isolated `scripts/revocation/registration-smoke.ts` covers missing approvals/checkpoints, stale or lagging feeds, scope mismatch, rollback after an insertion-trigger failure, concurrent idempotency, subsequent signed revocation and tombstone denial even if a binding is accidentally un-revoked. It uses a temporary local PostgreSQL cluster and fresh synthetic packs. The adapter is not called by S4 runtime; expected-reference authority storage, actual PA reference transport, operational credentials and release checks remain pending.

Registration audit disposition: the candidate now checks retained inbox coverage from zero (`count = max(sequence) = cursor`, using the positive sequence primary key) before mapping, rejecting nonzero bootstrap or pruned history. This scan is acceptable for isolated correctness acceptance only; operational scale needs a durable, permission-protected coverage/retention design before deployment. It is not a claim that privileged database administrators cannot forge history.

`ExpectedGrantReference.grantVersion` is the sole version authority because frozen ProcessingGrant has no version field. It must come from authenticated PA observed-snapshot metadata, persisted independently of uploads; manual copying from manifest is forbidden. Acquiring that authority remains a rollout gate. The adapter compares it with the approved manifest and uses existing trusted grant/source checks; a version mismatch is tested. Registration errors retain a generic external message with a bounded internal cause code, allowing tests to distinguish missing approval, stale checkpoint, scope mismatch, bootstrap gap, export watermark and tombstone rejection. A direct SQL insert independently confirms the tombstone trigger, including ON CONFLICT behavior. The current lowercase UUID schema is retained; operational DELETE privileges and mandatory runtime mapping remain future gates.

Final local osstack task_623dcfe6 passes registration and consumer PostgreSQL smoke suites, typecheck, lint and diff checks. One verified Claude CLI claude-opus-5-5 review; coverage and diagnostic fixes are host-verified, not independently re-audited. The existing CI workflow now runs the registration smoke in the same bounded job. Real PA reference transport and scoped operational-role testing are not included in this evidence.

## Candidate retained evidence guards

`retention-guards.sql` prevents UPDATE/DELETE/TRUNCATE of inbox evidence and DELETE/TRUNCATE of binding mappings; the existing mapping trigger already rejects UPDATE. It is separate from automatic migrations. This reduces the chance that a non-owner writer accidentally prunes tombstones or removes the mapping needed for future revocation. A dedicated isolated test grants a non-owner synthetic role the relevant DML privileges and proves that mutation, truncation, trigger disabling and replication-role bypass are rejected. The existing consumer transaction smoke also runs with these guards installed.

This is not a defense against privileged DDL administrators, not operational credential provisioning, and not an account-erasure policy. An explicit reviewed erasure/retention procedure remains required before deployment. Registration still checks complete retained inbox coverage; these guards do not replace that check or solve its production-scale cost. No live database or production role is modified.

Opus5.5 retention review found no trigger-semantic defect and requested a more explicit DDL/parameter-privilege boundary plus a mapping UPDATE negative test. SQL headers and PASS text now specify the owner/superuser/SET-parameter exclusions; the non-owner writer's mapping UPDATE is rejected by the pre-existing immutable mapping guard. Final osstack task_044fdabf passes retention and consumer suites, typecheck, lint and diff checks. Final clarification/test additions are host-verified, not separately re-audited. The existing CI job includes the retention smoke.

## Candidate protected database operation

`withRegisteredCandidate` is a candidate transaction boundary for a trusted database-only callback. It requires an existing approved, unrevoked binding and exactly one mapping matching the independently trusted feed/source/grant/version; it checks database-clock grant expiry, exact scope, a caught-up fresh checkpoint and absence of a matching tombstone. It holds the canonical owner advisory lock and repeats the checks before commit/return. Failed post-checks roll back callback database writes and withhold its returned result. Callbacks must not perform network, file, notification or other external side effects because those cannot be rolled back.

This primitive is not wired into S4 `bindingFor` or any HTTP route and does not enable a feature flag. Existing source/payload/manifest integrity checks remain required at actual call sites; the helper does not replace them. Operational pool privileges, authority sourcing and efficient retained-history assurance remain prerequisites. Synthetic acceptance proves missing mapping prevents callback execution, a registered read succeeds, stale state at the post-check rolls back a write, and revocation blocks access.

Two isolated `claude-opus-5-5` access reviews completed. Initial retained-coverage gap is fixed: access checks count=max=cursor as registration does. This remains an O(n) candidate check, requiring a scalable durable assurance design before production. Consumer already took the canonical owner advisory lock; the second review received its source. Acceptance now proves both lock orders using matching PostgreSQL advisory lock keys and holder PID, real elapsed checkpoint and grant expiry with rolled-back writes, exact mapping negatives, independent retained tombstone denial after resetting the binding, and fail-closed denial after admin-simulated pruning. Specific safe error causes distinguish expiry, tombstone and coverage failures without raw database errors.

The second review's conditional uppercase tombstone concern does not apply to the supported writer: `feed.ts` enforces lowercase UUIDs and positive int32 grant versions before inbox writes; a signed uppercase fixture is rejected with no inbox insertion. Direct privileged malformed writes remain outside this candidate's operational guarantee. No schema redesign was introduced to accommodate data rejected by the protocol. Trusted callback code must not control transactions or change security tables; it is not a SQL sandbox. Production integration must enforce bounded transaction/work duration and provision restricted writers. Expiry is checked at database-clock sampling points, not a promise of zero elapsed time through COMMIT/network delivery. Final additions are host-verified, not a third independent audit.

## Same-client transaction composition

`withRegisteredCandidateInTransaction` allows an authorized caller to use its existing PostgreSQL client, avoiding a nested pool connection waiting on its own owner lock. Entry requires explicit READ COMMITTED and no assigned transaction ID (no prior writes/row locks). It then assigns and verifies a stable transaction ID across lock acquisition and callback execution. This intentionally permits one protected callback per clean outer transaction; compose the complete business operation inside that callback and commit immediately afterward. Existing session/role checks and read-only owner authorization may precede entry. Neither helper is wired into S4 routes yet.

A verified Opus5.5 composition audit identified catch-and-COMMIT and uncommitted security-state hazards. Both are addressed: non-clean entry is denied, and errors poison the unchanged outer transaction so COMMIT becomes ROLLBACK. Transaction identity is assigned only after the clean-entry check; a virtual-XID mechanism was unnecessary under the one-call-per-clean-transaction contract. A callback that changes transactions remains a contract violation; the helper denies its result without attempting to abort a different transaction. Savepoint recovery and transaction control are forbidden, as are security-table writes and external side effects. This is trusted application composition, not an arbitrary SQL sandbox.

Single-connection isolated tests cover autocommit/RR/non-clean rejection, callback visibility and caller rollback, real checkpoint expiry followed by an intentionally attempted COMMIT (returns ROLLBACK; no writes survive), and callback transaction escape. Clock sampling now follows coverage/tombstone queries to account for time spent scanning retained history. Final fixes are host-verified; deployment authority, scalable history, bounded work and request routing remain outstanding.

## Resolve already registered server references

`withStoredCandidateInTransaction` removes caller-supplied reference identity from protected operation call sites. It resolves exactly one previously provisioned binding_map/feed identity inside the clean READ COMMITTED transaction, after the owner lock, and reuses the before/after guard. The mapping is the existing persistence boundary created by trusted registration; no additional authority table or upload-derived fallback is introduced. Request writers must have no provisioning/identity-write privileges. This does not implement authenticated PA metadata acquisition or independently validate how an operator provisioned the record.

One verified Claude Opus5.5 review found that the first resolver draft looked up before the guard, so missing records bypassed transaction poisoning and raw DB errors could escape. Resolution now runs inside the guard's sanitized failure/poison boundary. Isolated tests use separate transactions for unknown owner/payload, malformed UUID and pre-aborted state, verify dirty unknown-reference attempts cannot commit, and exercise stored-reference success, actual expiry rollback and independent tombstone denial after binding reset. Missing/ambiguous rows fail closed. Final fixes host-verified. Mandatory S4 call-site adoption and operational role provisioning remain open; production stays hard-disabled.

## Registered S4 import integration candidate

The stored resolver passes its trusted identity to import, which checks source/grant/version/reference consistency with `prepareRevocationCandidate`, both approval hashes and the export watermark before even returning a duplicate.
