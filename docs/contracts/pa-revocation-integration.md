# Revocation integration constraints from existing PA code

Implementation checkpoint, 2026-10-04. This is an execution note, not a deployed interface.

PA currently stores one mutable row per `(user_id, grant_id)` in `pa_bridge_grant`. `ProcessingGrant` has no version counter. The current `pa_bridge_event` replacement is in migration `20260922120000_pa_reader_bridge.sql` (not only the original bridge migration). Rights changes update all grant policies for the source, then upsert the selected grant. Scope sequence also includes ordinary reading events. Therefore neither the current grant row nor filtered outbox positions can directly satisfy the new versioned contiguous revocation feed.

Next producer implementation must:

1. Add explicit grant-version snapshots and a separate per-scope revocation head/event sequence. Reuse the existing owner advisory lock order; allocate committed positions transactionally, not via a sequence that leaves rollback holes.
2. Preserve all affected prior grant versions on rights changes. Revoke all relevant source versions on source withdrawal and all relevant scope versions on scope revoke. An idempotent replay must not add another position.
3. Define an explicit cutover epoch. A newly recorded current snapshot is evidence only from cutover onward, not reconstructed historical consent. Legacy Alpha bindings with unknown version remain ineligible for production processing until explicitly rebound/reimported against a recorded snapshot.
4. Return head and bounded page from one consistent database snapshot with server publication time. Signing uses only that snapshot; a transport service must not forge a new heartbeat over stale cached state. Feed reading uses a narrow scoped identity, not a generic service-role endpoint.
5. Add export metadata associating source/grant/version with the exact signed candidate; preserve the existing additive schema/extension rules. Verify producer and consumer agree before release.

Next consumer implementation must add a trusted feed registration, narrow revocation-only role, owner-serialized inbox/cursor transaction, duplicate-ID consistency and rollback tests. Its transaction must revoke matching bindings before committing its new cursor. Ordinary S4 runtime credentials must not acquire revocation grants. `assertRevocationFresh` must use committed trusted checkpoints selected for the binding's exact scope, and grant-expiry checks remain separate.

Acceptance must exercise rollback between inbox and binding mutation, duplicate delivery after commit, missing pages, concurrent workers, scope separation, unknown legacy versions, and stale heartbeat rejection on actual write and display paths. The current pure verifier and freshness guard do not provide these database or runtime guarantees.

## Approved manifest reference adapter (candidate only)

`prepareRevocationCandidate` validates an existing operator-approved candidate through `prepareCandidate` before interpreting `manifest.extensions['pa.revocation_reference']`. The extension must match PA's `pa-grant-reference/v1` shape, the trusted registered feed and scope, and the verified source and grant. It validates canonical observation time (no later than the candidate manifest), a positive int32 grant version and an int64 decimal export watermark. Missing references are rejected; legacy versions are never guessed.

Manifest extensions are not covered by `payload_digest`. The existing `approvedManifestHash` check is therefore mandatory, alongside `approvedPayloadHash`. Changing only the reference while keeping payload bytes intact is rejected unless the trusted operator approval itself changes. This adapter does not create approvals and does not provide a new signature-verification endpoint; callers must not accept binding or feed registration from an upload.

The result is only validated metadata. It does not insert a binding map, advance a feed cursor, check a persisted tombstone or establish current freshness. Next, implement candidate registration in a READ COMMITTED owner-serialized transaction against the existing approved binding and exact registered feed; require a caught-up fresh checkpoint at least through the exported watermark and reject revoked versions. Production S4 remains hard-disabled.

Opus5.5 review identified an authority gap for an in-range but wrong grant version and loss of existing error codes. The adapter now also requires a trusted `ExpectedGrantReference` (source, grant and version as well as feed/scope) and compares all identity fields, including the existing trusted config's grant ID. This dependency must be derived from authenticated PA export metadata/operator registration, never copied from the uploaded extension. Obtaining and persisting that authority remains unimplemented; this helper is not wired to an endpoint. No invented grant_version field was added to the frozen ProcessingGrant schema.

Existing `prepareCandidate` errors now propagate unchanged. Tests distinguish manifest approval failures (`policy_blocked`), identity/metadata failures, actor/revoked binding rejection and input-size limits. The manifest-only substitution test changes a valid earlier observation time so rejection specifically proves the manifest hash gate. Missing-reference input first proves the base candidate validator succeeds. Final task_9c65db64 passes revocation and ingest tests, typecheck and lint; full default regression passed before these final audit fixes (task_7c507cf3). Final fixes host-verified, not independently re-audited. Observation time is descriptive cutover metadata, not a grant-validity proof; no arbitrary lower bound tied to article observation was introduced.

## Existing-binding registration transaction (candidate only)

`registerCandidateReference` loads an existing operator-approved binding from the database while holding the canonical owner advisory lock and binding/feed row locks under READ COMMITTED. It runs the approved candidate/reference checks against that stored binding, matches the exact registered feed scope, checks database-clock grant expiry and committed caught-up freshness, and requires the cursor to have reached the export watermark. Conflicting mappings for the same binding fail closed. Mapping insertion remains subject to the existing tombstone trigger, including duplicate delivery; no cursor or approval is created or updated.

The isolated `scripts/revocation/registration-smoke.ts` covers missing approvals/checkpoints, stale or lagging feeds, scope mismatch, rollback after an insertion-trigger failure, concurrent idempotency, subsequent signed revocation and tombstone denial even if a binding is accidentally un-revoked. It uses a temporary local PostgreSQL cluster and fresh synthetic packs. The adapter is not called by S4 runtime; expected-reference authority storage, actual PA reference transport, operational credentials and release checks remain pending.

Registration audit disposition: the candidate now checks retained inbox coverage from zero (`count = max(sequence) = cursor`, using the positive sequence primary key) before mapping, rejecting nonzero bootstrap or pruned history. This scan is acceptable for isolated correctness acceptance only; operational scale needs a durable, permission-protected coverage/retention design before deployment. It is not a claim that privileged database administrators cannot forge history.

`ExpectedGrantReference.grantVersion` is the sole version authority because frozen ProcessingGrant has no version field. It must come from authenticated PA observed-snapshot metadata, persisted independently of uploads; manual copying from manifest is forbidden. Acquiring that authority remains a rollout gate. The adapter compares it with the approved manifest and uses existing trusted grant/source checks; a version mismatch is tested. Registration errors retain a generic external message with a bounded internal cause code, allowing tests to distinguish missing approval, stale checkpoint, scope mismatch, bootstrap gap, export watermark and tombstone rejection. A direct SQL insert independently confirms the tombstone trigger, including ON CONFLICT behavior. The current lowercase UUID schema is retained; operational DELETE privileges and mandatory runtime mapping remain future gates.
