# Static audit — S4 market-policy planner

Scope note: read-only review of the four files as given. I did not execute anything, so every claim below is derived from reading the code; where I compute a date or weekday I say so and recommend asserting it in a test rather than trusting my arithmetic.

Line numbers refer to the files as pasted (`market-policy.ts` 1–32, `market-policy.test.ts` 1–24).

---

## P0 — blocks freezing/registration

### P0-1. `full` is a hand-transcribed boolean that nothing cross-checks against `regular_close`
**Location:** `market-policy.ts:16`, `:20`, `:25`; `market-policy.json` `regular_open`/`regular_close`/`timezone`.
**Trigger:** The entire start rule (`early_close_start: "skip"`) pivots on `s.full`. `regular_open`, `regular_close` and `timezone` are declared in the policy and **never read by any code path**. If the 2026-09-22 transcription mislabels one early close as `full: true` — Nov 27 or Dec 24 2026 are the exact candidates — the planner silently selects a 13:00 ET close as a start and no test fails, because the only calendar test is a hash.
**Fix:** Derive `full` instead of trusting it. At module load, validate every session: convert `open`/`close` to `America/New_York` (real tz conversion, not a fixed offset) and assert `open == regular_open`, and `full ⟺ close == regular_close`, `!full ⟺ close == 13:00`. Fail loudly at import; a frozen artifact that fails its own invariants must not be usable.
**Test:** A calendar-invariants suite, independent of the planner: (a) every `full` session closes 16:00 ET and every non-`full` closes 13:00 ET; (b) sessions per calendar year — I compute **251 for 2026** (261 weekdays minus the 10 listed holidays, all of which fall on weekdays); (c) no session date falls on a weekend or on any listed holiday; (d) the early-close set for 2026 is exactly `{2026-11-27, 2026-12-24}`.

Transcription traps worth asserting explicitly:
- **Jul 3 2026 is a Friday holiday** (Jul 4 is Saturday), so 2026 has **no** July early close. A transcriber working from muscle memory may have added `2026-07-02` as an early close or listed Jul 3 as a half day.
- DST: 2026 transitions Mar 8 and Nov 1. A 16:00 ET close is `20:00Z` in summer and `21:00Z` in winter. `2026-11-20T21:00:00.000Z` (test:18) is on the correct side. A manual transcription spanning 2026–2028 has six DST boundaries to get right and zero tests covering them.

### P0-2. The digest test is not the independent check it appears to be
**Location:** `market-policy.ts:6–7`; `market-policy.test.ts:7–8`.
**Trigger:** `digest(policy)` hashes the **parsed object**, not the file bytes. Two consequences: (a) the hash does not pin whitespace, key order, or duplicate keys — two materially different files can produce the same `MARKET_POLICY_HASH`; (b) if `*.json.sha256` was produced by `shasum market-policy.json`, the test can never pass, and if it was produced by the same `digest()` path, the test is circular — it compares a serializer against itself and proves nothing about the artifact on disk. Secondary: `shasum` output is `<hash>  <filename>`; `.trim()` does not strip the filename suffix.
**Fix:** Hash the raw bytes: `createHash('sha256').update(readFileSync(path)).digest('hex')`, and have the sidecar generated by a documented external command recorded in the handoff. Keep the parsed-object digest only if you additionally publish the canonicalization rule.
**Test:** Assert the byte digest against the sidecar; add a fixture test proving the digest changes when only key order changes, and a parse test asserting the sidecar contains a bare 64-hex string.

### P0-3. The initial-start / suspended-start ambiguity is unresolved and silently decided by code
**Location:** `market-policy.ts:16` (`findIndex(s => s.full)`), `:18` (slice anchored at `first`), `:20` (`candidates.filter(s => s.full)`).
**Trigger:** Two independent binary choices are made in code with no corresponding policy field:

1. **Where the 10-session wait clock starts.** `:18` slices from `first`, the first *full* session, so a skipped early close is excluded from the wait budget entirely. Walk test:15 — cutoff `2026-11-26T00:00:00Z`, eligible sessions are `[Nov 27 (early), Nov 30, Dec 1 …]`, `first = 1`, budget = Nov 30 → Dec 11. Under the equally defensible reading "wait at most 10 trading sessions from the first eligible trading session," the budget is Nov 27 → Dec 10. **`waitExpiresAt` differs by one session and no test asserts it.**
2. **Whether `early_close_start: "skip"` applies to post-suspension starts.** `:20` filters *all ten* candidates to `full`, so it applies. But `suspension: "wait_first_valid_close"` says *first valid close* — and an early close is a valid close; that is precisely why `window_count` includes them as endpoints. The policy asserts early closes are valid enough to end a window but the code assumes they are never valid enough to start one, including after a halt.

Because this is a pre-registration artifact, an unresolved disjunction in the registered rule is not a style issue: the `policy_selection_basis: "registered_before_any_price_window_results"` claim is void if the rule admits two answers.
**Fix:** Add two explicit policy fields — `max_wait_anchor: "first_eligible_trading_session" | "first_full_session"` and `suspension_start_early_close: "skip" | "accept"` — and branch on them. Also decide whether `max_wait_trading_sessions: 10` counts the intended start session; `:18`'s inclusive slice means you get 9 sessions of actual waiting, which contradicts the convention `window_count` spells out (`exclude_start_session`).
**Test:** Pin `waitExpiresAt` for the Nov-26 case under each configured value, and a case where an early close is the only session between cutoff and the next full session, asserting whether it appears in `candidates`. Add a test asserting `candidates.length` and the inclusive/exclusive wait semantics at exactly the boundary.

### P0-4. `endpoint_missing: "data_insufficient"` is unimplemented; every failure is `rule_unsupported`
**Location:** `market-policy.ts:13, 17, 19, 26, 29`; `market-policy.json` `endpoint_missing`, `calendar_out_of_range`.
**Trigger:** Five structurally different failures throw one indistinguishable string: unparseable input, cutoff before calendar start, no full session remaining, wait budget truncated by calendar end, and window endpoint past calendar end. The last one is specified as `data_insufficient` but emits `rule_unsupported` at `:29`. Separately, `calendar_out_of_range: "data_insufficient/rule_unsupported"` is a **slash-separated disjunction inside a frozen artifact** — the outcome classification is literally not pinned, so a post-hoc choice between the two is available.
**Fix:** Typed error with a `code` field, one code per condition (`invalid_input`, `calendar_out_of_range`, `no_valid_start`, `wait_budget_truncated`, `endpoint_missing`). Resolve `calendar_out_of_range` to a single value before freezing.
**Test:** One negative test per code asserting `err.code`, not the message. Current test:22 passes via `first < 0` at `:17`, not via any range check — it would pass for the wrong reason and is indistinguishable from a truncated-budget failure.

## P1 — correctness/robustness

### P1-5. No upper-bound range check; usable calendar range is silently ~70 sessions shorter than it looks
**Location:** `market-policy.ts:12` (checks `range[0]` only), `:19`, `:28`.
**Trigger:** `plan()` enforces that 10 wait sessions exist but **never checks that the longest window (60) fits**. A start planned in late 2028 returns successfully, then `observationWindowEnds` throws at `:28–29` when `start + 60` runs off the end. The effective last plannable session is roughly `end − (max_wait + max(windows))` and this is documented nowhere.
**Fix:** Explicit `cutoff > Date.parse(calendar.range[1])` check with its own code, and have `plan()` require `first + max_wait + max(windows_trading_sessions)` to exist.
**Test:** A start positioned so the wait fits but the 60-session window does not; assert `plan()` fails at plan time with the right code rather than failing later.

### P1-6. Timestamp identity by string equality
**Location:** `market-policy.ts:25` (`s.close === actualStartAt`).
**Trigger:** `'2026-11-20T21:00:00Z'` and `'2026-11-20T21:00:00.000Z'` and `'2026-11-20T16:00:00-05:00'` denote the same instant; two of the three throw `rule_unsupported`. Test:18 only passes because it hard-codes the calendar's exact serialization. A caller round-tripping through `new Date().toISOString()` or any JSON layer that normalizes will break, and the error blames the rule rather than the input format.
**Fix:** Compare `Date.parse(s.close) === Date.parse(actualStartAt)`; reject unparseable input with `invalid_input`.
**Test:** Same start expressed in three equivalent forms, all yielding identical endpoints.

### P1-7. Unvalidated structural invariants of `calendar.sessions`
**Location:** `market-policy.ts:15–18` (index arithmetic on a filtered array), `:28` (`sessions[start + n]`).
**Trigger:** Both functions assume `sessions` is sorted strictly ascending, deduplicated, and contains **trading days only**. If holidays were transcribed as entries with `full: false` rather than omitted, then `full` no longer means "early close," holidays enter the 10-session wait budget at `:18`, and `:28` counts holidays as trading sessions — every window end shifts. Nothing distinguishes these two encodings; test:15 passes under both.
**Fix:** Assert the invariants at load (strict monotonic `open`, `open < close` per session, no duplicate `date`, no weekend/holiday dates present), and add an explicit `kind: "full" | "early_close"` enum rather than an overloaded boolean.
**Test:** Invariant suite from P0-1; plus a mutation test that inserting a holiday row makes the suite fail.

### P1-8. `MARKET_POLICY` is exported mutable
**Location:** `market-policy.ts:5`.
**Trigger:** Consumers hold a live reference to the parsed object. A mutation after import changes observed rules while `MARKET_POLICY_HASH` (computed once at `:6`) still reports the frozen value — the hash actively certifies a state that no longer holds.
**Fix:** Deep-freeze before export; compute the hash from the frozen value.
**Test:** Assert `Object.isFrozen` and that a write attempt throws in strict mode.

### P1-9. ESM JSON imports lack import attributes; module specifiers are inconsistent
**Location:** `market-policy.ts:1–3`.
**Trigger:** `:3` uses an explicit `.js` extension (NodeNext style) while `:1–2` import JSON with no attribute. Under Node ESM / `NodeNext`, JSON imports require `with { type: 'json' }` and will fail at runtime; Vitest's bundler resolves them anyway, so **tests pass and production fails**.
**Fix:** `import policy from '…/market-policy.json' with { type: 'json' };` or load via `readFileSync` + `JSON.parse` (which also makes P0-2's byte hashing natural).
**Test:** A smoke test that imports the module under plain `node --experimental-vm-modules` / the real production resolver, not only under Vitest.

### P1-10. Returning ten `candidates` invites post-hoc start selection
**Location:** `market-policy.ts:20`.
**Trigger:** The rule specifies exactly one start (first full session) with the rest reachable only if suspension occurs. Returning a flat array of ten leaves the choice to the caller after prices are visible — the precise degree of freedom S4 exists to remove. There is also no input representing whether a suspension occurred, so the planner cannot itself resolve which candidate applies.
**Fix:** Return `{ start, fallbacks, waitExpiresAt }`, and take a suspension record as an explicit argument so resolution is a function of declared inputs.
**Test:** Assert `start` is the first full session and that resolving to a fallback requires a suspension record covering the earlier candidates.

### P1-11. "Suspension" is undefined in the frozen policy
**Location:** `market-policy.json` `suspension`.
**Trigger:** `"wait_first_valid_close"` does not say what counts as a suspension (regulatory halt? LULD pause? no-trade session?), who asserts it, or what evidence is recorded. An undefined trigger is a discretionary trigger.
**Fix:** Define the condition, its source, and its evidence field in the policy before freezing.
**Test:** Fixture-driven cases per suspension type.

## P2 — hygiene and test-design gaps

- **`readFileSync` with CWD-relative paths** — `test.ts:7–8`. Breaks under a different Vitest `root` or when run from a subdirectory. Fix: resolve from `import.meta.url`.
- **`Date.parse` on bare date strings** — `market-policy.ts:12`, `test.ts:22`. `'2029-01-01'` parses as UTC midnight while `'2029-01-01T00:00'` parses as local; mixing date-only `range` entries with datetime `open`/`close` is a latent off-by-hours. Fix: require full ISO-8601 with offset everywhere, validate with a regex.
- **Invalid input reported as `rule_unsupported`** — `market-policy.ts:11–13`. `Math.max` correctly propagates `NaN` so the guard does catch it, but a malformed timestamp is a caller error, not an unsupported rule. Covered by P0-4's fix.
- **Misleading test name** — `test.ts:14`. `'2026-11-26T00:00:00Z'` is **2026-11-25 19:00 ET**, i.e. Wednesday evening, not Thanksgiving. The test passes, but it does not test what its name claims, and the Z-vs-ET slip it embodies is exactly the bug class this suite should catch. Fix: use `2026-11-26T14:30:00-05:00` and name it for the behaviour being pinned.
- **No boundary test at `open == cutoff`** — `market-policy.ts:15` uses strict `>`, matching `start_rule`'s "strictly_after". Untested. Add cutoff exactly equal to a session open and assert that session is excluded.
- **`ends[1]` and `ends[2]` never asserted** — `test.ts:19`. The 20- and 60-session windows are where a transcription error surfaces: 60 sessions from 2026-11-20 lands in 2027, crossing the year boundary and the March DST transition. Assert all three endpoints.
- **No exhaustion test** — the path where all 10 candidates are consumed without a valid start is unreachable in the current suite.
- **No early-close-start test for `observationWindowEnds`** — `:25` requires `&& s.full`, so if P0-3 is resolved toward "accept," the two functions become inconsistent and `observationWindowEnds` rejects a legitimate start. Add a test that locks whichever resolution you choose across *both* functions.

## What the current suite actually proves

Worth stating plainly, because the suite reads stronger than it is: it pins one start date, one early-close skip, one 5-session endpoint, and one out-of-range rejection that passes via an unintended code path. It proves nothing about the 2026–2028 calendar's contents, nothing about `waitExpiresAt`, nothing about the 20/60 windows, nothing about DST handling, and — per P0-2 — quite possibly nothing about the frozen digests either.

The ordering I'd suggest: P0-1 and P0-2 first (they determine whether the artifact is trustworthy at all), then P0-3 (it changes the registered rule text, not just the code), then P0-4 and P1-5 together since they share an error-taxonomy fix.
