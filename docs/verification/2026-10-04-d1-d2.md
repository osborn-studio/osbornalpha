## Local acceptance

Use Node 22 and local PostgreSQL 17 (set `S4_POSTGRES_BIN` if needed), from a clean checkout without real dotenv files or inherited database settings.

```sh
npm ci
npm run test:db
npm run test:migrations
npm run typecheck
npm run lint
npm run build
```

`test:db` starts its own loopback cluster, applies ordered migrations, runs all Vitest tests once, requires all 12 critical suites to contain only passed assertions, then stops/removes that cluster. Missing state/suite, inventory drift, empty tests, skips and changed locked historical migration bytes fail verification. A normal `npm test` without the runner still supports lightweight development and is not sufficient database evidence.

The migration rehearsal inserts synthetic rows immediately before the recovered migration, completes the subsequent chain and compares it with a fresh database. It compares public schema including ACL and excluding owner differences and verifies old watchlist data/defaults and news/broker source-key backfill, perspective origin and selected ACL grants/revokes. It is **not** a complete production dump comparison or a Supabase permission/extension simulation. Local bootstrap intentionally uses synthetic auth/storage and a superuser migration role; runtime RLS suites use the restricted application role.

Reports contain only sanitized summaries under ignored `reports/`. Do not upload state files, temporary database directories, passwords or full dotenv contents.

## Release hold

Before merging any migration-bearing PR, verify the production branch's automatic migration/branching paths and ensure mutations flow through the agreed release executor. These settings are currently unknown for this batch. Before production use, verify database major version, platform-role migration compatibility, actual migration history, current backup/recovery and release ownership. Local green tests cannot close these gates.

Ubuntu setup uses the [official PostgreSQL Apt repository procedure](https://www.postgresql.org/download/linux/ubuntu/) and explicitly installs version 17. GitHub Linux execution must be observed separately; successful macOS execution is not Linux CI evidence.

All existing migration bytes are locked against the repository snapshot (not a production hash assertion). Future migrations append after the locked maximum version; modifying the lock requires explicit review. Cleanup also exercises an already-stopped cluster. Reports distinguish actual PostgreSQL version from production equivalence.

The rehearsal alone enables explicit default table grants to exercise revocation, and requires UPDATE on the sibling alerts table while denying it on alert events. This targeted bootstrap is not enabled for the ordinary database test suites and still does not claim full Supabase parity.
