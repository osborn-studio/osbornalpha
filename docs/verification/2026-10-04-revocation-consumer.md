# Revocation candidate persistence acceptance

The candidate consumer verifies the signed raw page against operator-configured key/scope, takes the same owner advisory lock as S4, locks its feed row and atomically inserts inbox events, marks exact mapped source/grant/version bindings revoked and commits the new cursor/watermark. The immediately preceding byte-identical signed page is a no-op duplicate; it never refreshes publication time. Another occurrence of an existing revocation ID at a later sequence fails the transaction rather than hiding producer inconsistency.

`npm run test:revocation-consumer` creates an owned temporary PostgreSQL 17 cluster, applies the normal migrations plus `scripts/revocation/candidate-schema.sql`, and uses synthetic registrations/bindings and Ed25519 keys. It checks failure after inbox/binding writes rolls everything back, wrong scope rejects, concurrent duplicate delivery applies only once, other grant versions/owners remain untouched, and duplicate-ID conflict does not advance the cursor. It does not use developer env files or production credentials.

The schema is deliberately outside automatic migrations. This is real candidate persistence code and database verification, not a deployed consumer. Local tests use the temporary cluster admin; least-privilege runner credentials, forced RLS/functions, live feed producer, durable registration/key rotation, protected-route freshness wiring and operator cutover are still required. No production connection or release is authorized by these results.

An owner-serialized mapping trigger rejects registration of any source/grant/version already present in the inbox and forbids mapping updates. Unmapped revocations remain durable tombstones. The real import adapter still needs to register mappings transactionally and honor that rejection; until it is wired, this code must not be used operationally. A mapping is trusted operator state and must not be derived from unverified uploaded candidate fields. Legacy bindings without grant-version evidence must not silently acquire a guessed version.

First isolated Opus5.5 review found three blockers: late mapping resurrection, weak cross-owner test, and insufficient negative-test discrimination. Added the tombstone mapping trigger; same payload/source/grant/version in another owner/feed; conditional post-write failure trigger; successful fresh-ID control; and signed wrong-scope input. Second independent review confirmed those fixes and found canonical UUID lock-key, isolation and lock-contention coverage gaps. Consumer now hashes UUID-canonical text and explicitly starts READ COMMITTED; mapping registration rejects other isolation levels. Deterministic tests observe advisory-lock waits in both insertion orders, repeat with uppercase owner UUIDs and reject REPEATABLE READ registration. Final changes are host-verified, not third-party re-reviewed.

Candidate execution has local statement/connect timeouts in the harness; signal requests wait for bounded cleanup rather than bypassing teardown. No operational SLO or privileged production runner is provided. The same scope/feed epoch must survive recovery, or an explicit cutover must reconcile old tombstones; a new feed ID does not automatically inherit prior revocations.
