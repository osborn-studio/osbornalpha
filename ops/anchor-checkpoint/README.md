# Independent anchor checkpoint registry (C1)

Owner-only installation on the Shanghai managed PostgreSQL instance, per ADR `docs/adr/2026-10-18-anchor-runner-and-checkpoint.md` §4 and §8 item 2. Status: **schema and client exist; nothing is installed or enabled.** The registry stores owner-scope hashes, sequences, receipt hashes and generations, never article or judgment content.

## What it must survive

A rollback of the Alpha database (Supabase) **and** of the journal on the Lighthouse host. Therefore it lives on a different provider and region, outside both of those backup boundaries, and is never restored together with them. Its own backup can still lose confirmed rows; the runner then pauses (`registry_behind_cache`) rather than trusting the database.

## Install (once, as instance administrator)

1. Create a dedicated database and two NOLOGIN roles. Do not reuse `brain_deletion_ledger` or its roles.

   ```sql
   create database alpha_anchor_checkpoint;
   create role alpha_checkpoint_owner nologin nosuperuser nobypassrls nocreaterole nocreatedb;
   create role alpha_checkpoint_client nologin nosuperuser nobypassrls nocreaterole nocreatedb;
   grant create on database alpha_anchor_checkpoint to alpha_checkpoint_owner;
   revoke temporary on database alpha_anchor_checkpoint from public;
   ```

2. Connected to `alpha_anchor_checkpoint`, apply `schema.sql` as the schema owner (`set role alpha_checkpoint_owner;` then the file). The script refuses to run as a login or superuser role. Then `revoke create on schema public from public;`.

3. Register the deployment identity. Both UUIDs are generated by the operator and recorded in the runner manifest and in `research_s4_runtime_identity`; they are never auto-discovered.

   ```sql
   set role alpha_checkpoint_owner;
   select anchor_private.register_identity('<database_identity>', '<store_id>', 1);
   ```

4. Create the runner's login and keep its credential only on the Lighthouse host (0600, systemd `EnvironmentFile`):

   ```sql
   create role alpha_checkpoint_app login password '<random, >= 32 chars>' nosuperuser nobypassrls inherit;
   grant alpha_checkpoint_client to alpha_checkpoint_app;
   ```

   The login can execute `identity_state`, `latest_checkpoint` and `confirm_checkpoint` and nothing else. Verify with `\dp anchor_private.*` that no table privilege exists for the client role.

5. Open the instance security group for the Lighthouse host's public `/32` on 5432 only, TLS required. Record the server certificate chain the host must verify.

## Runner environment

```text
ALPHA_ANCHOR_REGISTRY_HOST=<instance host name, as in the certificate>
ALPHA_ANCHOR_REGISTRY_PORT=5432
ALPHA_ANCHOR_REGISTRY_DATABASE=alpha_anchor_checkpoint
ALPHA_ANCHOR_REGISTRY_USER=alpha_checkpoint_app
ALPHA_ANCHOR_REGISTRY_PASSWORD=<secret>
```

A connection URL is refused by the client; TLS verifies the certificate against the host name; `ALPHA_ANCHOR_REGISTRY_INSECURE_LOOPBACK=1` is accepted only for `127.0.0.1` in tests. The client budget is 4.5 s per request; a deadline or lost response is reported as `unknown` and retried with the same request id, which the registry answers as a duplicate.

## Generation advance (runner replacement, host rebuild, restore)

Advance here first, then in the journal header, then in `research_s4_runtime_identity`; a runner whose manifest generation is lower is refused by all three.

```sql
set role alpha_checkpoint_owner;
select anchor_private.advance_generation('<database_identity>', 2, 'host rebuild 2026-..');
```

## Measured latency

From the Singapore host to this instance, the deletion-ledger diagnostic saw 2.5–4.5 s per request (Brain `docs/deployment/deletion-ledger/SINGAPORE-LATENCY.md`). The runner therefore confirms checkpoints **after** the SQL acknowledgement commit and outside the owner lock; evaluation of the newly anchored sequences stays pending until the confirmation returns.
